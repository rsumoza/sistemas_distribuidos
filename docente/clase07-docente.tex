\section{Objetivo pedagógico profundo}

La clase debe reemplazar la intuición “Kafka es una cola rápida” por un modelo más preciso: el log conserva historia, la partición define orden, el offset define progreso y la frontera transaccional define qué se hace visible junto. El estudiante debe poder razonar sobre crashes sin depender de slogans.

\section{Resultados de aprendizaje}

\begin{itemize}
\item distinguir log, cola y base de estado;
\item elegir key y particiones a partir de orden y carga;
\item explicar position, committed offset, lag y rebalance;
\item derivar pérdida y duplicación desde timelines;
\item delimitar producer idempotence y exactly-once;
\item diseñar outbox, ventanas y stateful streaming;
\item proponer métricas y un SLO de extremo a extremo.
\end{itemize}

\section{Conducción paso a paso}

\subsection{Apertura}

Presente la campaña de pedidos y pregunte: “¿por qué no llamar sincrónicamente a inventario, email y analytics?”. Recoja beneficios y costos. Use las respuestas para introducir desacoplamiento temporal.

\subsection{Particiones}

Dibuje tres logs. Entregue eventos de dos pedidos y pida ubicarlos. Si los estudiantes mezclan keys, muestre cómo se pierde orden. Luego introduzca hot keys: una buena key semántica puede ser mala para distribución.

\subsection{Offsets}

Haga que cinco estudiantes representen poll, efecto, commit y crash. Cambie el orden. El grupo debe nombrar pérdida o duplicación. Solo después introduzca at-most-once y at-least-once.

\subsection{Exactly-once}

Escriba en el pizarrón tres columnas: entrega, estado, efecto externo. Pregunte en cuál vive cada garantía. Esta distinción evita la confusión más frecuente de la clase.

\subsection{Outbox}

Plantee el dual write sin nombrar el patrón. Pida a los grupos que intenten resolverlo cambiando el orden. Cuando descubran que ambas órdenes fallan, introduzca outbox como transformación de una transacción distribuida en una transacción local más entrega repetible.

\subsection{Streaming temporal}

Use un evento móvil tardío. Pregunte en qué minuto debe contarse. La discusión debe hacer emerger event time, processing time y watermarks.

\section{Casos reales y narrativa}

\subsection{Kafka en pipelines de actividad}

Use Kafka como ejemplo de commit log que permite múltiples consumidores y replay. Evite presentar un caso empresarial como argumento de autoridad; conecte siempre con las propiedades.

\subsection{Campaña de alto tráfico}

El ejemplo es familiar: el producer sigue aceptando pedidos mientras un consumidor se atrasa. Esto permite explicar que disponibilidad del broker y frescura del negocio son métricas distintas.

\subsection{Transactional outbox}

Use el caso pedido/evento. Enfatice que el relay puede duplicar y que la idempotencia no desaparece.

\section{Demostraciones sugeridas}

\begin{uademo}
\textbf{Offsets humanos.} Los estudiantes sostienen offsets. Mueva CRASH antes/después de commit y haga votar la semántica.
\end{uademo}

\begin{uademo}
\textbf{Hot partition.} Reparta 20 tarjetas de keys; 12 pertenecen al mismo cliente. Use hash simple y observe skew.
\end{uademo}

\begin{uademo}
\textbf{Outbox.} Dibuje DB y Kafka. Marque con una X cada ventana de fallo; luego agregue la fila outbox.
\end{uademo}

\section{Preguntas socráticas}

\begin{itemize}
\item ¿Qué orden necesita el negocio, exactamente?
\item ¿Quién es dueño del progreso: broker o consumidor?
\item ¿Qué ocurre si el efecto terminó pero el offset no?
\item ¿Qué duplicado resuelve el producer idempotente?
\item ¿Dónde termina la transacción de Kafka?
\item ¿Por qué outbox no elimina la necesidad de deduplicar?
\item ¿Qué latencia está midiendo el lag y cuál no?
\item ¿Cuánto tiempo esperaría por un evento tardío y por qué?
\end{itemize}

\section{Criterios de evaluación formativa}

Una respuesta lograda declara:
\begin{enumerate}
\item key y orden requerido;
\item particiones y supuesto de carga;
\item momento del commit de offset;
\item comportamiento ante crash;
\item efecto externo y estrategia idempotente;
\item métrica de lag/latencia.
\end{enumerate}

Use un semáforo rápido:
\begin{itemize}
\item rojo: producto sin semántica;
\item amarillo: semántica sin fallo;
\item verde: fallo, mecanismo y métrica;
\item azul: además identifica frontera y alternativa.
\end{itemize}

\section{Cómo mejorar la experiencia del estudiante}

\begin{itemize}
\item Mantenga un único caso conductor durante toda la clase.
\item Haga visibles los cambios de nivel: broker, consumidor, aplicación y negocio.
\item Use timelines antes que definiciones de semántica.
\item Permita que los grupos se equivoquen con dual write y descubran el patrón.
\item No use más de cinco siglas nuevas sin volver al diagrama.
\item Cierre cada concepto con un ejemplo real y un límite.
\item Recupere el exit ticket en la apertura de la clase 8.
\end{itemize}

Estas prácticas mejoran claridad, participación y percepción de utilidad, dimensiones que suelen pesar en encuestas docentes.
