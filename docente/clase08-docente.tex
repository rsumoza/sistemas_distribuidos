\section{Objetivo pedagógico profundo}

El objetivo es desmontar etiquetas superficiales. El estudiante debe salir capaz de decidir por operación y dominio. CAP se aprende mediante una partición concreta; Dynamo mediante conflictos y repair; Spanner mediante el costo explícito de coordinación y tiempo.

\section{Resultados de aprendizaje}

\begin{itemize}
\item formular CAP correctamente;
\item distinguir availability CAP de uptime;
\item usar PACELC para operación normal;
\item analizar $N,R,W$, versiones y reparación en Dynamo;
\item explicar TrueTime, consenso localizado y commit wait en Spanner;
\item diseñar una arquitectura híbrida por operación;
\item proponer pruebas de partición y SLOs.
\end{itemize}

\section{Conducción paso a paso}

\subsection{CAP desde un invariante}

No comenzar con el triángulo. Comenzar con dos retiros durante partición. Preguntar qué respondería cada región. Después nombrar la elección. Esto evita que los alumnos memoricen C/A/P sin entender el conflicto.

Aclare que P no se “elige” en una red real; se decide qué garantía mantener cuando ocurre.

\subsection{PACELC}

Use latencias concretas. Pregunte: “si la red está sana, ¿igual esperamos 180 ms?”. Muestre que el costo de consistencia existe también sin incidente.

\subsection{Dynamo}

Use el carrito porque el merge tiene significado intuitivo. Después contraste con asiento y saldo para mostrar límites. Haga físicamente quórums con tarjetas. Pregunte primero qué garantiza la intersección; corrija la conclusión “garantiza último valor”.

\subsection{Spanner}

No entrar primero en infraestructura GPS. Explique el problema: external consistency global. Luego TrueTime como intervalo y commit wait como costo. Cierre con consenso localizado para evitar la imagen de un consenso planetario único.

\section{Casos reales y narrativa}

\subsection{Dynamo}

Narrativa: Amazon prioriza una experiencia always-on para ciertos servicios y hace visibles versiones/conflictos. No diga “Amazon eligió AP para todo”.

\subsection{Spanner}

Narrativa: Google necesitaba transacciones globales fuertes y construyó infraestructura de consenso y tiempo acotado. No diga “Spanner viola CAP”; durante pérdida de quorum sacrifica disponibilidad.

\section{Demostraciones sugeridas}

\begin{uademo}
\textbf{Quórums humanos.} A,B,C; escritura A,B y lectura B,C. Luego escritura A y lectura C. Preguntar qué sabe cada lectura.
\end{uademo}

\begin{uademo}
\textbf{Version vectors.} Entregar tres vectores y pedir ordenar o declarar concurrencia.
\end{uademo}

\begin{uademo}
\textbf{TrueTime.} Dibujar intervalos solapados y no solapados; decidir cuándo puede afirmarse orden.
\end{uademo}

\section{Preguntas socráticas}

\begin{itemize}
\item ¿Qué invariante se rompe si ambos lados responden?
\item ¿Un error rápido cuenta como availability CAP?
\item ¿Qué cuesta coordinar cuando no hay partición?
\item ¿Qué garantiza intersección y qué no?
\item ¿Cuándo dos versiones son concurrentes?
\item ¿Quién paga por eventual consistency?
\item ¿Qué representa la anchura de TrueTime?
\item ¿Por qué no usar un consenso global único?
\item ¿Qué dato de su TP tolera merge y cuál no?
\end{itemize}

\section{Criterios de evaluación formativa}

Una respuesta lograda debe incluir:
\begin{enumerate}
\item dato/operación e invariante;
\item comportamiento durante partición;
\item costo latency/consistency normal;
\item mecanismo de coordinación o reparación;
\item SLO y prueba adversarial.
\end{enumerate}

\section{Cómo mejorar la experiencia del estudiante}

\begin{itemize}
\item Use casos contrastantes y no definiciones aisladas.
\item Haga que los alumnos tomen una decisión antes de mostrar la solución real.
\item Vuelva repetidamente al costo del error del negocio.
\item Separe con claridad CAP, PACELC, quorum, causalidad y linearizabilidad.
\item Entregue una matriz comparativa al cierre para facilitar estudio.
\item Permita que cada grupo aplique el concepto a su TP durante la clase.
\end{itemize}

Esto aumenta percepción de claridad, relevancia y transferencia, y favorece una valoración docente alta de forma genuina.

\section{Conexión con el Trabajo Final Integrador}

Solicitar una matriz por subsistema con: invariante, comportamiento bajo partición, decisión PACELC, mecanismo, repair y SLO. Revisar al menos una decisión en vivo por grupo.

\section{Cierre y puente}

Cierre: “La próxima clase ya no pregunta solo qué consistencia ofrece un datastore, sino cómo distribuimos responsabilidades entre servicios y equipos sin convertir el sistema en una red de dependencias frágiles”.
