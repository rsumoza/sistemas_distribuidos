\begin{frame}{Disponibilidad CAP: todo nodo no fallado debe responder}
\UASlideTag{NÚCLEO}{UAIngNavy}
\begin{itemize}
\item Toda request recibida por un nodo no fallado debe terminar con una respuesta; en la formulación clásica, responder con un error que niega el servicio no preserva availability.
\item No alcanza con responder rápido ``no sé'' o ``intente más tarde''.
\item Es una definición teórica estricta, distinta de ``99.99\% uptime''.
\end{itemize}
\begin{uawarn}
Bajo la definición CAP, rechazar una compra para proteger consistencia sacrifica disponibilidad aunque el proceso siga vivo.
\end{uawarn}
\end{frame}

\begin{frame}{PACELC es una taxonomía, no otro teorema CAP}
\UASlideTag{NÚCLEO}{UAIngNavy}
\begin{itemize}
\item CAP expresa una imposibilidad bajo un modelo y una partición concretos.
\item PACELC organiza decisiones arquitectónicas también cuando no hay partición.
\item No demuestra que toda base pertenezca para siempre a una sola casilla.
\item Un mismo producto puede ofrecer modos o garantías diferentes por operación.
\end{itemize}
\begin{block}{Uso correcto}
Emplear PACELC para formular preguntas sobre coordinación y latencia, no como etiqueta comercial definitiva.
\end{block}
\end{frame}

\begin{frame}{Qué no dice CAP}
\UASlideTag{NÚCLEO}{UAIngNavy}
\begin{itemize}
\item No dice que un sistema elija permanentemente dos letras.
\item No dice que todas las operaciones deban tomar la misma decisión.
\item No clasifica latencia normal: para eso PACELC es más útil.
\item No afirma que consistencia eventual sea ``datos incorrectos''.
\item No reemplaza el análisis de invariantes, repair, SLO o probabilidad de partición.
\end{itemize}
\begin{block}{Regla de uso}
Aplicar CAP a una operación, un dato, un invariante y una falla concretos.
\end{block}
\end{frame}

\UASectionSlide{Dynamo: disponibilidad y\\reconciliación explícita}

\begin{frame}{Por qué nació Dynamo}
\UASlideTag{NÚCLEO}{UAIngNavy}
\small
El paper de Amazon describe un key-value store para servicios que necesitaban una experiencia ``always-on''. Bajo ciertos escenarios, prioriza disponibilidad y acepta versiones que deben reconciliarse.
\begin{itemize}
\item Particionamiento mediante consistent hashing.
\item Replicación configurable con $N$, $R$ y $W$.
\item Versionado y resolución de conflictos asistida por la aplicación.
\item Sloppy quorum, hinted handoff y anti-entropy.
\end{itemize}
{\scriptsize Referencia: DeCandia et al., \emph{Dynamo: Amazon's Highly Available Key-value Store}.}
\end{frame}

\UASectionSlide{Spanner: consistencia externa\\con coordinación localizada}

\begin{frame}{Qué problema intenta resolver Spanner}
\UASlideTag{NÚCLEO}{UAIngNavy}
\small
Spanner fue diseñado como una base global, multi-versión y sincrónicamente replicada, capaz de ofrecer transacciones distribuidas externamente consistentes.
\begin{itemize}
\item Datos particionados en grupos de replicación.
\item Consenso localizado dentro de cada grupo.
\item Coordinación transaccional entre grupos cuando una operación cruza shards.
\item TrueTime expone incertidumbre temporal.
\end{itemize}
{\scriptsize Referencia: Corbett et al., \emph{Spanner: Google's Globally-Distributed Database}.}
\end{frame}

\begin{frame}{No hay un consenso global único}
\UASlideTag{NÚCLEO}{UAIngNavy}

\draw[uaArrow] (g1)--(tx); \draw[uaArrowO] (g2)--(tx); \draw[uaArrow] (g3)--(tx);

\begin{block}{Escalabilidad}
Particionar limita el dominio de consenso. Las operaciones multi-shard pagan coordinación adicional solo cuando la semántica lo exige.
\end{block}
\end{frame}

\begin{frame}{TrueTime formaliza incertidumbre}
\UASlideTag{NÚCLEO}{UAIngNavy}
\[
TT.now()=[t_{earliest},t_{latest}], \qquad \epsilon=t_{latest}-t_{earliest}
\]
\begin{itemize}
\item El reloj real se encuentra dentro del intervalo declarado.
\item Un intervalo más ancho implica mayor incertidumbre.
\item La infraestructura reduce $\epsilon$, pero no lo reemplaza por cero.
\end{itemize}
\begin{uakeybox}
El aporte conceptual es exponer la incertidumbre como dato del protocolo, no esconderla detrás de un timestamp aparentemente exacto.
\end{uakeybox}
\end{frame}

\begin{frame}{External consistency: orden visible compatible con el mundo}

\begin{frame}{Volvemos al diagnóstico inicial}
\UASlideTag{ACTIVIDAD}{UAIngOrange}
\small
\begin{enumerate}
\item \textbf{Falso:} CAP restringe el comportamiento durante partición; no es una elección permanente de dos letras.
\item \textbf{Falso:} una respuesta errónea sacrifica availability en el modelo CAP estricto.
\item \textbf{Falso:} la intersección no elimina concurrencia, sloppy quorum ni decisiones de lectura.
\item \textbf{Falso:} Dynamo conserva versiones y puede requerir reconciliación; LWW no es su única semántica.
\item \textbf{Falso:} TrueTime devuelve un intervalo que explicita incertidumbre.
\end{enumerate}
