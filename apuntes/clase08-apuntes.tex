\section{Propósito de la clase}

Esta clase toma conceptos que a menudo se enseñan como etiquetas y los vuelve decisiones de arquitectura. CAP, PACELC, Dynamo y Spanner no deben memorizarse como siglas o productos; deben usarse para responder una pregunta concreta: \emph{qué error es más costoso para este dominio y qué costo está dispuesto a pagar el sistema para evitarlo}.

Las clases previas ya mostraron que:
\begin{itemize}
\item la red puede partirse;
\item las réplicas pueden divergir;
\item el consenso impone un orden a costa de coordinación;
\item los logs y particiones ofrecen orden local, no global;
\item la aplicación debe definir qué significa un efecto correcto.
\end{itemize}

\begin{uakeybox}
La consistencia real no es una propiedad única del sistema. Es una política por dato y operación, condicionada por fallas, latencia y costo del error.
\end{uakeybox}

\section{CAP: formulación correcta}

El resultado CAP se aplica a sistemas de datos replicados cuando existe una partición de red. La formulación práctica es:
\begin{quote}
Durante una partición, no es posible garantizar simultáneamente una semántica de consistencia fuerte y disponibilidad para todas las solicitudes a nodos no fallados.
\end{quote}

\subsection{Consistencia}

En este contexto, consistencia suele interpretarse como una semántica fuerte comparable a linearizabilidad: las operaciones parecen ocurrir sobre una única copia y respetan el orden temporal observable.

No significa “los datos no están corruptos” ni “la aplicación es correcta” en un sentido general.

\subsection{Disponibilidad}

Disponibilidad CAP exige que cada solicitud a un nodo no fallado obtenga una respuesta no errónea, sin esperar indefinidamente la reconexión de otra partición.

Responder “no puedo atender ahora porque no tengo quorum” preserva corrección, pero renuncia a disponibilidad CAP para esa operación.

\subsection{Partición}

Una partición implica que grupos de procesos correctos no pueden intercambiar mensajes a tiempo para coordinar. No es simplemente “una máquina cayó”. Dos regiones pueden seguir sanas localmente y, aun así, quedar incapaces de sostener una historia única sin sacrificar respuestas.

\section{CAP como dos decisiones}

Ante una partición:
\begin{itemize}
\item una operación CP puede bloquear/rechazar para impedir historias incompatibles;
\item una operación AP puede responder en ambos lados y aceptar conflicto o inconsistencia temporal.
\end{itemize}

Ejemplo de saldo: dos regiones ven saldo 100. Durante una partición, cada una recibe un retiro de 80. Si ambas aceptan, el invariante puede romperse. Si una o ambas rechazan por falta de quorum, se preserva el invariante a costa de disponibilidad.

No hay una respuesta universal. Para un feed social, aceptar divergencia temporal puede ser razonable. Para un ledger, no.

\section{Qué no dice CAP}

\begin{itemize}
\item No dice que el sistema deba elegir una única letra para toda su vida.
\item No dice que las particiones estén siempre presentes.
\item No describe por sí solo la latencia cuando la red funciona.
\item No dice que todo modelo eventual sea equivalente.
\item No reemplaza el análisis de invariantes del dominio.
\end{itemize}

Un sistema puede ser CP para reservas y AP para analytics; puede ofrecer lecturas locales y escrituras coordinadas; puede degradar garantías explícitamente.

\section{PACELC}

PACELC amplía la conversación:
\begin{quote}
Si hay Partición, elegir entre Availability y Consistency; Else, elegir entre Latency y Consistency.
\end{quote}

Incluso sin partición, coordinar regiones remotas agrega tiempo de red, colas y disponibilidad de participantes. Una lectura local de perfil puede tardar 15 ms y estar atrasada; una lectura coordinada puede tardar 180 ms y ofrecer una garantía más fuerte.

PACELC obliga a preguntar por la ruta normal, no solo por el desastre. Esta perspectiva es especialmente útil en sistemas geodistribuidos.

\section{Dynamo: disponibilidad como requisito primario}

\subsection{Motivación real}

Dynamo fue diseñado para servicios de Amazon que necesitaban una experiencia “always-on”. El paper describe un key-value store altamente disponible que sacrifica consistencia en ciertos escenarios, usa versionado de objetos y permite resolución de conflictos asistida por la aplicación.

El carrito de compras es un caso emblemático: ante versiones concurrentes, perder un producto puede ser peor que mostrar la unión y permitir reconciliación posterior.

\subsection{Consistent hashing}

El espacio de claves se mapea a un anillo lógico. Los nodos poseen rangos y las claves se asignan según hash. Ventajas:
\begin{itemize}
\item incorporación/remoción de nodos con remapeo limitado;
\item particionamiento descentralizado;
\item posibilidad de virtual nodes para balancear capacidad.
\end{itemize}

Limitaciones:
\begin{itemize}
\item distribución uniforme de claves no garantiza distribución uniforme de acceso;
\item hot keys siguen existiendo;
\item la topología física y la diversidad de fallas requieren una estrategia de réplica.
\end{itemize}

\subsection{N, R y W}

\begin{itemize}
\item $N$: número de réplicas preferidas;
\item $W$: respuestas requeridas para aceptar escritura;
\item $R$: respuestas requeridas para completar lectura.
\end{itemize}

Si $R+W>N$, cualquier conjunto de lectura y escritura del tamaño indicado intersecta. Esa propiedad aumenta la posibilidad de observar una versión actualizada, pero no garantiza automáticamente linearizabilidad.

¿Por qué no basta?
\begin{itemize}
\item las escrituras pueden ser concurrentes;
\item sloppy quorums pueden usar nodos fuera del conjunto preferido;
\item la lectura debe reconciliar versiones y elegir una política;
\item “última escritura” puede depender de relojes no confiables;
\item pueden existir respuestas parciales y timeouts.
\end{itemize}

\subsection{Ejemplo de intersección}

Con $N=3$, $W=2$, $R=2$, una escritura a A,B y una lectura a B,C comparten B. Sin embargo, si existen versiones concurrentes o B aún no expone la nueva versión según la política, la intersección combinatoria no define por sí sola toda la semántica.

Con $W=1$, $R=1$, la escritura puede quedar solo en A y la lectura ir a C: se obtiene una versión anterior con baja latencia y alta disponibilidad.

\section{Version vectors y conflicto}

Un version vector registra conocimiento causal por réplica/actor. Una versión domina a otra si contiene todo su conocimiento y algún avance. Si ninguna domina, las versiones son concurrentes.

Esto permite distinguir:
\begin{itemize}
\item actualización posterior: puede reemplazar una versión anterior;
\item actualización concurrente: requiere merge, política o intervención.
\end{itemize}

Last-write-wins es simple, pero puede perder información si usa relojes desalineados o si el dominio no admite descartar una rama. Un carrito puede fusionarse por unión de ítems; un asiento único o saldo no admite ese merge ingenuo.

\section{Sloppy quorum y hinted handoff}

Para mantener disponibilidad, Dynamo puede aceptar una escritura en nodos alternativos si los preferidos están inaccesibles. El nodo temporal guarda un hint para reenviar el dato al propietario cuando se recupere.

Beneficios:
\begin{itemize}
\item disponibilidad de escritura durante fallas;
\item menor dependencia de una lista rígida de réplicas.
\end{itemize}

Costos:
\begin{itemize}
\item datos temporalmente fuera de lugar;
\item lecturas y reparaciones más complejas;
\item mayor duración de divergencia;
\item riesgo de acumulación de hints.
\end{itemize}

\section{Read repair, anti-entropy y Merkle trees}

Eventual consistency necesita trabajo de convergencia.

\subsection{Read repair}
Durante una lectura, el coordinador detecta versiones atrasadas y escribe la versión reconciliada en las réplicas.

\subsection{Anti-entropy}
Procesos de background comparan rangos y reparan diferencias aunque no haya lecturas.

\subsection{Merkle trees}
Un árbol de hashes resume rangos de claves. Si las raíces difieren, se desciende hasta localizar rangos divergentes y transferir solo lo necesario.

La reparación consume red, CPU y disco. Si la tasa de divergencia supera la capacidad de repair, “eventual” puede volverse operacionalmente demasiado tarde.

\section{Spanner: consistencia externa a escala global}

\subsection{Objetivo real}

Spanner fue diseñado como una base multi-versión, globalmente distribuida y replicada sincrónicamente, capaz de ofrecer transacciones externamente consistentes.

No intenta maximizar disponibilidad bajo toda partición. Su prioridad es una historia global fuerte para aplicaciones que necesitan transacciones y SQL distribuidos.

\subsection{Particionamiento y consenso localizado}

Spanner particiona datos y replica cada grupo mediante consenso. No existe un único consenso planetario para cada operación. Las transacciones que abarcan varios grupos coordinan participantes.

Este punto es crucial: escalar consistencia fuerte requiere localizar consenso y evitar que toda operación contacte a todo el sistema.

\section{TrueTime}

TrueTime expone un intervalo:
\[
TT.now()=[earliest,latest]
\]
que garantiza contener la hora real. La anchura del intervalo representa incertidumbre.

En lugar de asumir relojes perfectos, Spanner construye una infraestructura para medir y acotar incertidumbre mediante múltiples fuentes y monitoreo.

La lección conceptual es amplia:
\begin{quote}
Una buena abstracción distribuida no siempre elimina incertidumbre; puede exponerla con una garantía útil.
\end{quote}

\section{External consistency y commit wait}

External consistency exige que si una transacción termina antes de que otra comience, ese orden se refleje en la serialización.

Spanner asigna un timestamp de commit y espera hasta que TrueTime garantice que ese timestamp quedó en el pasado antes de hacer visible el commit. Esta espera se conoce como commit wait.

Beneficio:
\begin{itemize}
\item orden externo fuerte y lecturas consistentes con tiempo real.
\end{itemize}

Costo:
\begin{itemize}
\item latencia adicional incluso sin partición;
\item infraestructura temporal compleja;
\item dependencia de consenso y conectividad suficiente.
\end{itemize}

Este es un ejemplo claro de PACELC: en operación normal, se paga latencia para consistencia.

\section{Dynamo y Spanner: preguntas distintas}

\begin{tabular}{p{0.22\textwidth}p{0.34\textwidth}p{0.34\textwidth}}
\toprule
Dimensión & Dynamo & Spanner \\
\midrule
Objetivo & disponibilidad y baja latencia & transacciones globales fuertes \\
Partición & responde y reconcilia & puede rechazar por falta de quorum \\
Conflicto & versiona/merge & evita mediante orden/transacción \\
Operación normal & favorece local y configurable & paga consenso y commit wait \\
Costo principal & reparación y semántica de aplicación & coordinación e infraestructura \\
\bottomrule
\end{tabular}

No deben evaluarse como si uno fuera “mejor”. Cada uno es coherente con un dominio distinto.

\section{Diseño por operación}

Un sistema real puede combinar:
\begin{itemize}
\item feed eventual y local;
\item perfil con read-your-writes para el dueño;
\item reserva de asiento serializable;
\item cache con stale-while-revalidate;
\item analytics por log;
\item ledger con consenso fuerte.
\end{itemize}

La arquitectura madura elige la garantía mínima suficiente por operación. Esto reduce coordinación innecesaria sin sacrificar invariantes críticos.

\section{Casos de dominio}

\subsection{Carrito de compras}

Prioridad: disponibilidad. Conflictos fusionables. Dynamo-like puede ser razonable.

\subsection{Reserva de asiento}

Prioridad: unicidad. No se puede vender dos veces el mismo asiento. Se necesita coordinación fuerte o partición de autoridad con fencing.

\subsection{Feed social}

Prioridad: latencia y disponibilidad. Un orden aproximado y frescura eventual son aceptables, con excepciones para privacidad/bloqueos.

\subsection{Ledger financiero}

Prioridad: invariantes, auditabilidad y serialización. Se acepta mayor latencia y rechazo durante pérdida de quorum.

\section{Método de decisión}

Para cada dato y operación:
\begin{enumerate}
\item definir el invariante;
\item medir costo de inconsistencia;
\item definir comportamiento bajo partición;
\item definir costo de coordinación sin partición;
\item elegir autoridad, quorum, merge o reparación;
\item definir SLI/SLO;
\item ensayar falla y recuperación.
\end{enumerate}

\section{Errores frecuentes}

\begin{itemize}
\item repetir “dos de tres”;
\item clasificar una empresa entera como AP o CP;
\item confundir availability CAP con uptime genérico;
\item asumir linearizabilidad por $R+W>N$;
\item usar LWW para datos no descartables;
\item no dimensionar anti-entropy;
\item diseñar consenso global único;
\item ignorar latencia normal entre regiones;
\item comparar sistemas sin declarar dominio e invariante.
\end{itemize}

\section{Conexión con el Trabajo Final Integrador}

Cada grupo debe presentar una matriz por subsistema:
\begin{itemize}
\item invariante;
\item decisión bajo partición;
\item decisión latency/consistency normal;
\item mecanismo: quorum, líder, merge, saga o cache;
\item reparación;
\item SLO y prueba de falla.
\end{itemize}

No se acepta “nuestro sistema es CP” como análisis completo. Deben discutir operaciones concretas.

\section{Síntesis final}

\begin{uakeybox}
Dynamo hace visible el costo de responder durante fallas: versiones, merge y repair. Spanner hace visible el costo de una historia global fuerte: consenso, tiempo acotado y espera. Diseñar consistencia es elegir conscientemente cuál de esos costos paga cada operación.
\end{uakeybox}
