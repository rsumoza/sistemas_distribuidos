\section{Introducción}

Los sistemas de almacenamiento constituyen la base sobre la cual se implementan las abstracciones de transacciones, consistencia y concurrencia. A diferencia de los modelos lógicos, aquí debemos enfrentar restricciones físicas reales:

\begin{itemize}
\item latencia de disco
\item costo de fsync
\item diferencia entre acceso secuencial y aleatorio
\end{itemize}

\begin{quote}
El diseño del storage engine define los límites reales del sistema.
\end{quote}

---

\section{Write-Ahead Logging (WAL)}

\subsection{Principio fundamental}

Antes de modificar cualquier dato persistente, el sistema debe registrar la operación en un log estable:

\[
\text{WAL write} \rightarrow \text{Data write}
\]

\subsection{Propiedad clave}

Esto garantiza:

\begin{itemize}
\item \textbf{Atomicidad}: operaciones incompletas pueden revertirse
\item \textbf{Durabilidad}: operaciones confirmadas pueden recuperarse
\end{itemize}

---

\subsection{Modelo de recuperación}

Sea un log:

\[
L = \{op_1, op_2, ..., op_n\}
\]

En caso de crash:

\begin{itemize}
\item \textbf{REDO}: reaplicar operaciones committed
\item \textbf{UNDO}: revertir operaciones no committed
\end{itemize}

---

\subsection{Problema sin WAL}

Si se escribe primero el dato:

\begin{itemize}
\item crash puede dejar estado inconsistente
\item no hay forma de reconstruir
\end{itemize}

---

\section{MVCC (Multi-Version Concurrency Control)}

\subsection{Idea central}

En lugar de sobrescribir datos:

\begin{quote}
cada escritura crea una nueva versión
\end{quote}

\subsection{Modelo formal}

Cada objeto:

\[
x = \{(v_1, t_1), (v_2, t_2), ...\}
\]

Una transacción con timestamp $t$ lee:

\[
\max \{v_i \mid t_i \le t\}
\]

---

\subsection{Ventaja principal}

\begin{itemize}
\item lectores no bloquean escritores
\item escritores no bloquean lectores
\end{itemize}

Esto elimina conflictos RW.

---

\subsection{Problemas}

\begin{itemize}
\item crecimiento de versiones
\item necesidad de garbage collection
\end{itemize}

---

\subsection{Garbage Collection}

Una versión puede eliminarse si:

\[
t_{version} < \min(\text{timestamps activos})
\]

---

\section{LSM Trees}

\subsection{Motivación}

Discos favorecen escrituras secuenciales:

\[
\text{secuencial} \gg \text{aleatoria}
\]

---

\subsection{Arquitectura}

\begin{itemize}
\item WAL (durabilidad)
\item Memtable (estructura en memoria)
\item SSTables (archivos inmutables en disco)
\end{itemize}

---

\subsection{Flujo de escritura}

\begin{enumerate}
\item escribir en WAL
\item insertar en Memtable
\item flush a SSTable
\item compaction
\end{enumerate}

---

\subsection{Compaction}

Proceso de merge:

\begin{itemize}
\item combina múltiples SSTables
\item elimina versiones antiguas
\item reduce fragmentación
\end{itemize}

---

\subsection{Problemas}

\begin{itemize}
\item write amplification
\item read amplification
\end{itemize}

---

\section{Índices}

\subsection{B-Tree}

\begin{itemize}
\item estructura balanceada
\item acceso en $O(\log n)$
\end{itemize}

---

\subsection{Comparación}

\begin{itemize}
\item LSM: alto throughput de escritura
\item B-Tree: baja latencia de lectura
\end{itemize}

---

\section{Integración}

Un storage engine moderno combina:

\begin{itemize}
\item WAL → durabilidad
\item MVCC → concurrencia
\item LSM/B-Tree → organización física
\end{itemize}

---

\section{Conclusión}

\begin{quote}
El almacenamiento no es una implementación: es la materialización del modelo de consistencia.
\end{quote}

Para estudiar el tema con profundidad conviene reconstruir cuatro preguntas: \emph{qué problema aparece}, \emph{qué garantía se desea}, \emph{qué mecanismo la aproxima} y \emph{qué costo introduce}. En cada ejemplo debe identificarse además el modelo de falla implícito.

\end{uakeybox}

\section{Profundización autocontenida v9}
\subsection{Problema, límite e invariante}
El núcleo de esta clase es WAL, checkpoints, recovery, MVCC, B-trees, LSM trees, Bloom filters y amplificaciones. Para estudiarlo de manera autónoma conviene separar tres planos. Primero, el \emph{problema observable}: qué comportamiento incorrecto puede ver un cliente o un operador. Segundo, el \emph{límite del modelo}: qué información, sincronía o coordinación no está disponible. Tercero, el \emph{invariante}: qué propiedad no debe violarse aunque el sistema pierda progreso temporalmente.

El modelo de fallas relevante incluye crash entre WAL y datos, corrupción parcial, compaction atrasada y versiones retenidas. Una solución debe describirse como protocolo y no solo como nombre de tecnología: actores, estados, mensajes, condición de éxito, condición de aborto y estado visible después de una interrupción. La evidencia esperada es log de recovery, benchmark de lectura/escritura y medición de amplificaciones.

\subsection{Método de análisis}
Ante un caso nuevo, siga esta secuencia:
\begin{enumerate}
\item Identifique actores, dato o recurso compartido y frontera de confianza.
\item Escriba una ejecución nominal y una ejecución adversarial.
\item Distinga seguridad (lo malo no ocurre) de progreso (algo bueno finalmente ocurre).
\item Declare qué supuesto permite avanzar: mayoría, deadline, sincronía parcial, operación idempotente, almacenamiento durable u otro.
\item Compare una alternativa más simple y una más fuerte; registre qué métrica o experimento haría cambiar la decisión.
\end{enumerate}

\subsection{Caso transferible}
Considere una plataforma de reservas que recibe operaciones duplicadas, pierde conectividad entre regiones y debe sostener un camino crítico sin ocultar el estado real al usuario. Aplique el mecanismo de esta clase a una única decisión concreta. Una respuesta madura no intenta resolver todo: delimita la operación, formula la garantía y explica la degradación esperada cuando el supuesto central deja de cumplirse.

\subsection{Errores de razonamiento frecuentes}
\begin{itemize}
\item confundir una propiedad con el producto que suele implementarla;
\item describir el camino feliz sin recorrer una falla intermedia;
\item afirmar ``exactly-once'', ``alta disponibilidad'' o ``consistencia'' sin definir alcance observable;
\item medir solo throughput aunque la hipótesis trate sobre semántica o recuperación;
\item presentar la complejidad añadida como beneficio sin compararla con la alternativa más simple.
\end{itemize}
