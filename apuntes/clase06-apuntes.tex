\section{Propósito y mapa de la clase}

Las primeras cinco clases construyeron un lenguaje para razonar sobre incertidumbre, comunicación remota, replicación, consenso y transacciones. Esta clase responde una pregunta que a menudo queda oculta detrás de esas abstracciones: \emph{¿qué debe ocurrir físicamente para que las garantías sigan siendo verdaderas después de una falla?}

Cuando una API devuelve \texttt{200 OK}, cuando una réplica declara una entrada \emph{committed} o cuando una base de datos confirma \texttt{COMMIT}, existe una cadena de mecanismos que debe convertir decisiones lógicas en bytes recuperables. Esa cadena incluye buffers, page cache, registros de log, páginas de datos, versiones, índices, checkpoints y políticas de mantenimiento.

\begin{uakeybox}
El almacenamiento no es una implementación secundaria. Es la capa donde atomicidad, durabilidad, aislamiento y rendimiento adquieren significado operativo.
\end{uakeybox}

Los objetivos de la clase son:
\begin{itemize}
\item recuperar los conceptos esenciales de las clases 1 a 5 y conectarlos con mecanismos físicos;
\item explicar la frontera entre una escritura aceptada, una escritura replicada y una escritura durable;
\item comprender Write-Ahead Logging, checkpoints y recuperación;
\item comprender MVCC como administración explícita de versiones y snapshots;
\item comparar B-trees y LSM-trees a partir de cargas reales;
\item razonar sobre write, read y space amplification;
\item formular decisiones de almacenamiento mediante evidencia y no mediante preferencias de producto.
\end{itemize}

\section{Repaso recuperativo de las clases 1 a 5}

\subsection{Clase 1: incertidumbre y observación parcial}

En un sistema distribuido, un componente no observa directamente el estado interno de otro. Si un cliente no recibe respuesta, no puede distinguir con certeza entre request perdido, servidor lento, servidor caído, operación ejecutada con respuesta perdida o partición de red. Esta indistinguibilidad tiene una consecuencia directa para el almacenamiento: una operación debe tener una identidad y un resultado durable si se desea que los reintentos sean seguros.

Ejemplo: un cliente envía \texttt{POST /transferencias} y recibe timeout. Si el servidor no conserva un identificador idempotente junto con el resultado, el retry puede crear una segunda transferencia. La idempotencia no se resuelve solo en la API; requiere persistir la relación entre intención lógica y efecto realizado.

\subsection{Clase 2: RPC, timeout, retry e idempotencia}

Un retry mejora progreso frente a fallas transitorias, pero puede repetir una operación ya ejecutada. Para una operación no naturalmente idempotente, el servidor suele:
\begin{enumerate}
\item recibir una clave idempotente estable;
\item buscar si la operación lógica ya fue procesada;
\item ejecutar y persistir efecto y resultado como una unidad coherente;
\item devolver el mismo resultado ante reintentos.
\end{enumerate}

La pregunta física es inmediata: ¿en qué momento la clave y el resultado son suficientemente durables como para responder al cliente? Si se responde antes de cruzar esa frontera, un crash puede borrar el registro y volver inseguro el retry.

\subsection{Clase 3: replicación y consistencia}

Replicar y persistir no son sinónimos. Una copia en RAM de tres nodos puede perderse con una falla común; una copia persistente en un único dispositivo puede sobrevivir un crash local, pero no la destrucción del dispositivo. También es posible que varias réplicas sean durables y, aun así, representen versiones divergentes.

Por lo tanto, una política de confirmación debe declarar qué evento considera suficiente:
\begin{itemize}
\item recepción en memoria local;
\item append al WAL local;
\item \texttt{fsync} local;
\item persistencia en una réplica remota;
\item persistencia en una mayoría;
\item aplicación a la estructura de datos principal.
\end{itemize}

Cada elección cambia latencia, disponibilidad y probabilidad de pérdida.

\subsection{Clase 4: consenso y orden lógico}

Raft y Paxos acuerdan un orden de entradas. Sin embargo, el acuerdo lógico necesita un soporte físico. Si un nodo “recuerda” un voto o una entrada solo en memoria y reinicia, puede violar las premisas de seguridad del algoritmo. Por eso, los protocolos de consenso especifican qué estado debe persistirse antes de emitir ciertas respuestas.

Una frase útil es:
\begin{quote}
El consenso decide qué debe recordarse; el storage engine determina si realmente puede recordarse después de un crash.
\end{quote}

\subsection{Clase 5: transacciones y serializabilidad}

Atomicidad y durabilidad requieren log y recuperación. El aislamiento puede implementarse con locks, validación optimista o versiones. Snapshot Isolation se apoya típicamente en MVCC, pero no equivale a serializabilidad: dos transacciones pueden leer el mismo snapshot y escribir elementos distintos, generando write skew.

La clase 5 definió el contrato. La clase 6 estudia parte de su implementación física.

\section{La frontera de durabilidad}

\subsection{Una llamada a write no es necesariamente un dato durable}

Entre una aplicación y el medio persistente existen varias capas: buffer de usuario, runtime, page cache del sistema operativo, controlador, cache del dispositivo y medio físico. Una operación puede retornar cuando los bytes llegaron a una capa volátil. Por eso, la durabilidad depende de la semántica de \texttt{fsync}, de la configuración de hardware y del protocolo de recuperación.

Esto explica por qué “la aplicación escribió el archivo” no es una prueba suficiente. El sistema necesita definir una frontera de persistencia y medir el costo de cruzarla.

\subsection{Costo de fsync y group commit}

Forzar almacenamiento estable en cada operación puede ser costoso. Los motores agrupan varios commits para amortizar una sincronización física. El beneficio es mayor throughput; el costo es que las transacciones comparten una espera y que la latencia puede crecer bajo carga.

Un punto pedagógico importante es que el batching no debilita necesariamente la durabilidad si todos los participantes reciben confirmación solo después de que el grupo ha sido persistido. Cambia la forma de pagar el costo, no la garantía declarada.

\section{Write-Ahead Logging}

\subsection{La regla WAL}

Write-Ahead Logging impone un orden entre log y páginas:
\begin{enumerate}
\item el registro que describe una modificación debe llegar al log durable antes de que la página modificada pueda escribirse al almacenamiento principal;
\item el registro de commit debe ser durable antes de confirmar la transacción al cliente.
\end{enumerate}

La ventaja es que las páginas de datos pueden escribirse de forma diferida y en un orden eficiente. Si ocurre un crash, el log contiene información suficiente para rehacer cambios confirmados que aún no estaban reflejados en las páginas.

\subsection{Caso real: PostgreSQL}

La documentación oficial de PostgreSQL explica que no es necesario forzar cada página modificada en cada commit. Si el WAL es durable, la recuperación puede hacer \emph{roll-forward} y reaplicar cambios que no llegaron a los archivos de datos. Esta decisión reduce I/O aleatorio en el camino crítico y convierte el log secuencial en la base de la durabilidad.

No debe interpretarse como “PostgreSQL no escribe datos”. Significa que la escritura de páginas se desacopla temporalmente de la confirmación, bajo una regla de orden segura.

\subsection{REDO y UNDO}

Los diseños de recovery varían. Conceptualmente:
\begin{itemize}
\item REDO reaplica cambios de transacciones confirmadas que faltan en las páginas;
\item UNDO elimina efectos de transacciones que no alcanzaron commit.
\end{itemize}

Algunos motores usan estrategias que minimizan o evitan UNDO físico mediante MVCC, páginas copy-on-write o reglas de no-propagación. El mensaje central no es memorizar una única implementación, sino entender qué información necesita recovery para distinguir historia confirmada de trabajo incompleto.

\subsection{Ejemplo paso a paso}

Supongamos una transacción que actualiza $x$ de 3 a 5:
\begin{enumerate}
\item se agrega al WAL el registro de cambio;
\item se modifica la página en memoria;
\item se agrega y persiste el registro de commit;
\item se responde al cliente;
\item ocurre un crash antes de escribir la página de datos;
\item recovery encuentra el commit y rehace la modificación.
\end{enumerate}

Si el crash hubiese ocurrido antes del registro durable de commit, recovery no debería presentar la transacción como confirmada.

\section{Checkpoints y tiempo de recuperación}

Un checkpoint establece un punto desde el cual recovery puede comenzar sin releer toda la historia. Suele implicar:
\begin{itemize}
\item registrar un punto consistente;
\item escribir o programar la escritura de páginas sucias;
\item conservar WAL suficiente para recuperar desde ese punto;
\item coordinar con replicación, backups y snapshots.
\end{itemize}

El intervalo de checkpoint es un trade-off:
\begin{itemize}
\item más frecuente: menor recovery, mayor presión de escritura y riesgo de picos;
\item menos frecuente: menor trabajo de checkpoint durante operación, mayor WAL y recovery más largo.
\end{itemize}

El objetivo no es “hacer muchos checkpoints”, sino cumplir un objetivo de recuperación sin destruir la latencia normal.

\section{MVCC: concurrencia mediante múltiples versiones}

\subsection{Idea central}

Multi-Version Concurrency Control conserva múltiples versiones de un dato. Una transacción lee las versiones visibles según su snapshot, mientras nuevas escrituras crean versiones posteriores. Esto permite que lectores y escritores avancen con menor bloqueo mutuo.

Un modelo simplificado para una versión es:
\[
(x, valor, inicio, fin)
\]
La versión es visible si el snapshot de la transacción cae dentro de su intervalo de validez y la transacción que la creó es visible según las reglas del motor.

\subsection{Snapshot coherente}

Una transacción de lectura que comienza en $t_s$ puede seguir viendo el estado correspondiente a $t_s$ aunque otras transacciones confirmen nuevas versiones. Esta propiedad es muy útil para reportes largos, backups consistentes y lecturas repetibles.

Sin MVCC, una alternativa sería bloquear escritores durante toda la lectura o aceptar que el reporte mezcle estados de momentos diferentes.

\subsection{Caso real: PostgreSQL y VACUUM}

En PostgreSQL, una actualización crea una nueva versión de fila y deja la versión anterior disponible hasta que ninguna transacción pueda verla. Cuando las versiones dejan de ser necesarias, \texttt{VACUUM} permite reutilizar el espacio y mantener saludables tablas e índices.

Una transacción muy larga puede mantener snapshots antiguos y retrasar la limpieza. Esto genera bloat, más páginas que leer, más trabajo de vacuum y presión sobre índices. El caso muestra que MVCC no “elimina” el costo de concurrencia: lo transforma en costo de retención y garbage collection.

\subsection{MVCC y anomalías}

MVCC es un mecanismo, no un modelo único de aislamiento. Dependiendo de las reglas del motor, puede ofrecer Read Committed, Repeatable Read, Snapshot Isolation o Serializable. Snapshot Isolation evita varias anomalías, pero puede admitir write skew.

Por lo tanto, la pregunta correcta no es “¿usa MVCC?”, sino “¿qué historia permite observar y qué conflictos detecta antes de commit?”.

\section{B-trees e índices orientados a páginas}

\subsection{Por qué B-tree funciona bien en OLTP}

Un B-tree usa nodos con alto fan-out para mantener poca altura. Cada nodo suele alinearse con una página del almacenamiento. La búsqueda requiere pocas lecturas y soporta igualdad, rangos y orden.

El índice es particularmente útil para patrones como:
\begin{itemize}
\item buscar una cuenta por identificador;
\item listar pedidos de un cliente ordenados por fecha;
\item recorrer un rango de timestamps;
\item encontrar el siguiente valor mayor o menor.
\end{itemize}

\subsection{Costo de mantenimiento}

Cada índice adicional aumenta:
\begin{itemize}
\item trabajo de inserción y actualización;
\item espacio;
\item WAL generado;
\item trabajo de vacuum o compaction;
\item probabilidad de page splits y cache misses.
\end{itemize}

Por eso, “crear un índice para acelerar” no es suficiente. Deben observarse planes de ejecución, selectividad, cardinalidad, distribución de datos y carga de escritura.

\subsection{Índices compuestos}

El orden de columnas importa. Para una consulta que filtra por \texttt{cliente\_id} y ordena por fecha, un índice compuesto puede evitar tanto el scan como el sort. Sin embargo, ese mismo índice puede ser poco útil para consultas que solo filtran por la segunda columna.

El diseño de índices es diseño de carga, no diseño de esquema aislado.

\section{LSM-trees}

\subsection{Motivación}

Las LSM-trees convierten muchas escrituras aleatorias en una secuencia de appends y merges. El camino típico es:
\begin{enumerate}
\item persistir en WAL;
\item insertar en una memtable ordenada;
\item congelar y hacer flush a una SSTable inmutable;
\item fusionar SSTables mediante compaction.
\end{enumerate}

Esta arquitectura es atractiva para ingestión intensa, telemetría, series temporales y stores clave-valor.

\subsection{Lecturas}

Una lectura puede necesitar consultar memtable, SSTables recientes y niveles compactados. Para reducir I/O se usan:
\begin{itemize}
\item índices por archivo;
\item Bloom filters;
\item block cache;
\item compaction que limita solapamiento;
\item búsqueda desde datos más recientes hacia más antiguos.
\end{itemize}

Los tombstones representan eliminaciones y deben conservarse hasta que sea seguro eliminar versiones antiguas en todos los niveles relevantes.

\subsection{Compaction}

Compaction fusiona runs ordenados, retiene la versión necesaria y elimina datos obsoletos cuando es seguro. No es un proceso gratuito: lee y reescribe datos que la aplicación quizá no modificó recientemente.

RocksDB ofrece diferentes estrategias porque cada una redistribuye costo:
\begin{itemize}
\item leveled compaction suele reducir read y space amplification, pero puede aumentar write amplification;
\item tiered o universal compaction reduce parte de la reescritura, pero puede aumentar runs consultados y espacio temporal;
\item FIFO es apropiada para ciertos logs con TTL y requisitos simples.
\end{itemize}

\subsection{Write stalls y backpressure}

Si el ritmo de ingreso supera durante demasiado tiempo la capacidad de flush y compaction, se acumulan archivos y niveles. La latencia de lectura y el espacio empeoran. Un motor responsable desacelera o detiene escrituras para evitar una degradación sin límite.

La documentación de RocksDB denomina \emph{write stalls} a esta regulación. Es un ejemplo concreto de backpressure dentro de un storage engine.

\section{Las tres amplificaciones}

\subsection{Write amplification}

Relación entre bytes físicos escritos y bytes lógicos modificados. WAL, índices, compaction, replicación y backups pueden multiplicar escritura.

\subsection{Read amplification}

Cantidad de estructuras o bloques consultados para responder una lectura. En una LSM puede crecer si existen muchos runs; en un B-tree puede crecer por cache misses, bloat o mala selectividad.

\subsection{Space amplification}

Relación entre espacio físico y estado lógico vivo. Versiones MVCC, tombstones, archivos solapados, índices y espacio temporal de compaction contribuyen.

Estas tres dimensiones rara vez se minimizan simultáneamente. La ingeniería consiste en elegir una forma del costo compatible con la carga y los SLO.

\section{Comparación razonada: B-tree y LSM}

\begin{tabular}{p{0.23\textwidth}p{0.34\textwidth}p{0.34\textwidth}}
\toprule
Criterio & B-tree & LSM-tree \\
\midrule
Write path & actualización de páginas e índices & WAL, memtable, flush y compaction \\
Point lookup & pocas páginas, comportamiento estable & varios runs; Bloom y cache ayudan \\
Range scan & natural por orden del árbol & eficiente si hay pocos runs y buena compaction \\
Carga típica & OLTP equilibrado o read-heavy & ingestión intensa y write-heavy \\
Costo diferido & vacuum, splits, reindex & compaction, tombstones, stalls \\
\bottomrule
\end{tabular}

No se debe concluir que “B-tree es para lectura y LSM para escritura” como regla absoluta. La implementación, cache, hardware, tamaño de datos, compaction y patrón de consultas pueden invertir resultados. La frase sirve como orientación inicial, no como benchmark.

\section{Dos casos de diseño}

\subsection{Ledger bancario}

Requisitos:
\begin{itemize}
\item baja latencia predecible;
\item transacciones y rangos temporales;
\item invariantes estrictos;
\item carga de lectura y escritura equilibrada;
\item auditoría y recovery controlado.
\end{itemize}

Una solución relacional con WAL, B-tree y MVCC puede ser razonable. Esto no evita evaluar replicación, checkpoints, índices y aislamiento.

\subsection{Telemetría IoT}

Requisitos:
\begin{itemize}
\item alto throughput de ingestión;
\item append por dispositivo y timestamp;
\item retención temporal;
\item consultas por rango y agregaciones;
\item tolerancia a frescura eventual en vistas analíticas.
\end{itemize}

Una LSM-tree con compaction orientada a tiempo, particionamiento y Bloom filters puede ser razonable. Deben medirse stalls, lag de compaction, espacio y latencia de rango.

\section{Método para tomar la decisión}

Use la secuencia:
\begin{enumerate}
\item describir carga: ratios, tamaño, skew y crecimiento;
\item declarar garantías: durabilidad, recovery, aislamiento y frescura;
\item elegir mecanismo inicial;
\item identificar el costo desplazado;
\item definir métricas y experimento;
\item revisar la elección con evidencia.
\end{enumerate}

Métricas relevantes:
\begin{itemize}
\item latencia p50/p95/p99 de lectura y escritura;
\item throughput sostenible;
\item bytes WAL por byte lógico;
\item write/read/space amplification;
\item tiempo de checkpoint y crash recovery;
\item tamaño de backlog de compaction;
\item cache hit rate;
\item bloat o versiones retenidas.
\end{itemize}

\section{Aplicación del marco del curso}

\[
D=(P,F,G,S,T)
\]

Ejemplo para telemetría:
\begin{itemize}
\item $P$: ingerir y consultar eventos a alta tasa;
\item $F$: crash, backlog de compaction, pérdida de dispositivo, picos de carga;
\item $G$: pérdida máxima acotada, recovery dentro de objetivo, rangos consultables;
\item $S$: WAL, LSM, replicación, compaction y retención;
\item $T$: más write amplification, latencia de compaction y consistencia eventual en vistas.
\end{itemize}

\section{Errores conceptuales frecuentes}

\begin{itemize}
\item confundir write exitoso con write durable;
\item asumir que replicación sustituye a persistencia;
\item creer que MVCC elimina todas las anomalías;
\item crear índices sin observar costo de mantenimiento;
\item tratar compaction como mantenimiento gratuito;
\item elegir una estructura por nombre de producto y no por carga;
\item medir solo throughput medio e ignorar colas y p99;
\item ignorar recovery hasta el primer incidente.
\end{itemize}

\section{Síntesis final}

\begin{uakeybox}
WAL hace recuperable una historia confirmada; MVCC administra historias concurrentes; B-trees y LSM-trees organizan el acceso físico. Ningún mecanismo es gratuito. El diseño correcto convierte garantías y cargas en decisiones medibles de persistencia, versiones, índices y mantenimiento.
\end{uakeybox}
