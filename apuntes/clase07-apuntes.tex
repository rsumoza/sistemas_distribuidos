\section{Introducción}

El paradigma moderno de sistemas distribuidos se basa en \textbf{event sourcing} y \textbf{logs inmutables}. En lugar de mutar estado directamente, los sistemas registran eventos que luego pueden ser reproducidos.

\begin{quote}
El estado es una función del log: $State = f(Log)$
\end{quote}

\section{Commit Log}

Un commit log es una secuencia ordenada e inmutable:

\[
L = (e_0, e_1, e_2, \dots)
\]

Cada evento $e_i$ tiene un offset $i$.

\subsection{Propiedades}
\begin{itemize}
\item \textbf{Inmutabilidad}: no se modifica, solo append
\item \textbf{Orden}: total dentro de la partición
\item \textbf{Reproducibilidad}: permite reconstruir estado
\end{itemize}

\section{Kafka}

\subsection{Modelo}

Un topic se divide en particiones:

\[
Topic = \{P_0, P_1, ..., P_k\}
\]

Cada partición es un log independiente.

\subsection{Orden}

El orden está garantizado solo dentro de cada partición.

\subsection{Replicación}

Cada partición tiene:
\begin{itemize}
\item líder (acepta writes)
\item seguidores (replican)
\end{itemize}

\section{Offsets}

Los offsets permiten:
\begin{itemize}
\item control de progreso
\item relectura (replay)
\item tolerancia a fallas
\end{itemize}

\section{Semánticas de entrega}

\subsection{At-most-once}

Commit antes de procesar:

\begin{itemize}
\item pérdida posible
\item sin duplicación
\end{itemize}

\subsection{At-least-once}

Commit después de procesar:

\begin{itemize}
\item duplicación posible
\item sin pérdida
\end{itemize}

\subsection{Exactly-once}

Requiere:

\begin{itemize}
\item idempotencia (procesamiento repetible)
\item control transaccional de offsets
\item coordinación productor-consumidor
\end{itemize}

\section{Streaming}

\subsection{Modelo}

Procesamiento continuo:

\begin{itemize}
\item eventos entrantes
\item transformaciones
\item salidas
\end{itemize}

\subsection{Stateful streaming}

Ejemplo:

\begin{itemize}
\item conteo de eventos por ventana
\item joins entre streams
\end{itemize}

\section{Fallas y recuperación}

\begin{itemize}
\item duplicación: retry
\item pérdida: commit temprano
\item reorder: múltiples particiones
\end{itemize}

\section{Conclusión}

\begin{quote}
El log es la base de sistemas modernos; los servicios son transformaciones del log.
\end{quote}

\section{Profundización autocontenida v9}
\subsection{Problema, límite e invariante}
El núcleo de esta clase es commit logs, Kafka, particiones, consumer groups, offsets, exactly-once lógico, event time y estado. Para estudiarlo de manera autónoma conviene separar tres planos. Primero, el \emph{problema observable}: qué comportamiento incorrecto puede ver un cliente o un operador. Segundo, el \emph{límite del modelo}: qué información, sincronía o coordinación no está disponible. Tercero, el \emph{invariante}: qué propiedad no debe violarse aunque el sistema pierda progreso temporalmente.

El modelo de fallas relevante incluye replay, rebalanceo, commit prematuro o tardío de offsets y evento fuera de orden. Una solución debe describirse como protocolo y no solo como nombre de tecnología: actores, estados, mensajes, condición de éxito, condición de aborto y estado visible después de una interrupción. La evidencia esperada es offsets, lag, replay, resultados idempotentes y checkpoints de estado.

\subsection{Método de análisis}
Ante un caso nuevo, siga esta secuencia:
\begin{enumerate}
\item Identifique actores, dato o recurso compartido y frontera de confianza.
\item Escriba una ejecución nominal y una ejecución adversarial.
\item Distinga seguridad (lo malo no ocurre) de progreso (algo bueno finalmente ocurre).
\item Declare qué supuesto permite avanzar: mayoría, deadline, sincronía parcial, operación idempotente, almacenamiento durable u otro.
\item Compare una alternativa más simple y una más fuerte; registre qué métrica o experimento haría cambiar la decisión.
\end{enumerate}

\subsection{Caso transferible}
Considere una plataforma de reservas que recibe operaciones duplicadas, pierde conectividad entre regiones y debe sostener un camino crítico sin ocultar el estado real al usuario. Aplique el mecanismo de esta clase a una única decisión concreta. Una respuesta madura no intenta resolver todo: delimita la operación, formula la garantía y explica la degradación esperada cuando el supuesto central deja de cumplirse.

\subsection{Errores de razonamiento frecuentes}
\begin{itemize}
\item confundir una propiedad con el producto que suele implementarla;
\item describir el camino feliz sin recorrer una falla intermedia;
\item afirmar ``exactly-once'', ``alta disponibilidad'' o ``consistencia'' sin definir alcance observable;
\item medir solo throughput aunque la hipótesis trate sobre semántica o recuperación;
\item presentar la complejidad añadida como beneficio sin compararla con la alternativa más simple.
\end{itemize}
